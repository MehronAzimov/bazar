# План разработки «Базар-навигатор»

Положите этот файл в `docs/PLAN.md`. Рядом должны лежать `docs/TZ.md` и `docs/PZ.md`, а в корне проекта — `CLAUDE.md`.

## Как пользоваться

1. Каждый шаг — это **одна сессия Claude Code**. Начали шаг — закончили — проверили — закоммитили.
2. Для любого шага используйте один и тот же промпт:

```
Выполни шаг <НОМЕР> из docs/PLAN.md.
Сначала коротко расскажи, что собираешься сделать и какие файлы создашь, и дождись моего «да».
После выполнения запусти тесты, отметь шаг как выполненный в docs/PLAN.md
и скажи, как мне проверить результат вручную.
```

3. Проверьте результат по пункту «Проверка» у шага. Если всё работает:
```
Сделай коммит с понятным описанием на русском.
```
4. Если что-то сломалось, вставьте **полный текст ошибки**:
```
При проверке шага <НОМЕР> получаю ошибку:
<вставить текст ошибки целиком>
Найди причину и исправь. Не меняй то, что не относится к ошибке.
```
5. Перед новым шагом начинайте новую сессию (`/clear` или новый запуск `claude`).

Чекбоксы `[ ]` Claude будет отмечать сам, так вы всегда видите, где остановились.

## Этап 0. Подготовка (≈ 1–2 недели)

### [x] 0.1. Каркас бэкенда
**Что делаем:** проект `backend/` на Spring Boot 3, Java 21, Gradle (Kotlin DSL). Зависимости: Web, Security, Data JPA, Validation, WebSocket, Flyway, PostgreSQL, springdoc-openapi, Actuator, Lombok, Testcontainers. Файл `docker-compose.yml` в корне с PostgreSQL 16 (с расширением pg_trgm) и MinIO. `.env.example`, `.gitignore`, `README.md` с командами запуска. Пустая миграция `V1__init.sql`, которая включает pg_trgm. Security на этом шаге пропускает всё.
**Проверка:** `docker compose up -d`, затем `./gradlew bootRun`; открывается `http://localhost:8080/actuator/health` (статус UP) и `http://localhost:8080/swagger-ui.html`.
**Примечание:** образ `minio/minio` сейчас недоступен для анонимного `docker pull` (ни Docker Hub, ни quay.io/ghcr.io) — сервис MinIO оставлен в `docker-compose.yml` по ТЗ, проверим его в шаге 1.4, когда он понадобится. Postgres-часть проверена полностью; порт Postgres в этом проекте — 5433 (на 5432 у разработчика локальный Homebrew-Postgres).

### [ ] 0.2. Общая инфраструктура
**Что делаем:** глобальная обработка ошибок в формате RFC 7807 (код, сообщение, поле с ошибкой) с сообщениями на русском и таджикском; базовый класс сущности (id, created_at, updated_at, deleted_at); настройка Jackson (даты ISO 8601 в UTC); профили `dev` и `prod`; логирование; GitHub Actions, который запускает `./gradlew test` на каждый push.
**Проверка:** `./gradlew test` проходит; запрос на несуществующий адрес возвращает JSON-ошибку правильного формата.

## Этап 1. MVP (≈ 6–8 недель)

### Бэкенд

### [ ] 1.1. Модуль auth — вход по номеру телефона
**Что делаем:** таблицы `users`, `devices`; вход по SMS-коду: `POST /auth/otp/send`, `POST /auth/otp/verify`, `POST /auth/refresh`, `POST /auth/logout`. Код из 6 цифр, живёт 5 минут, 5 попыток, хранится хешем. Интерфейс `SmsSender` с реализацией-заглушкой, которая пишет код в лог (настоящий SMS-провайдер подключим позже). JWT: access 15 минут, refresh 30 дней с ротацией. Роли: BUYER, SELLER, ADMIN, MODERATOR, AGENT. Ограничение частоты через Bucket4j (5 кодов в час на номер, 20 на IP). `GET /me`, `PATCH /me`.
**Проверка:** в Swagger запросить код, взять его из лога, получить токены, вызвать `/me` с токеном.

### [ ] 1.2. Модуль map — базары, ряды, места
**Что делаем:** таблицы `cities`, `bazaars`, `rows`, `places`, `points_of_interest` по разделу «Модель базы данных» из ТЗ. Названия на 4 языках. Публичные `GET /bazaars`, `GET /bazaars/{id}`, `GET /bazaars/{id}/map` (ряды, места, точки интереса одним ответом). CRUD для ADMIN под `/admin/api/...`.
**Проверка:** через Swagger под админом создать город, базар, 2 ряда, 5 мест; `GET /bazaars/{id}/map` возвращает всё вместе.

### [ ] 1.3. Модуль catalog — магазины и товары
**Что делаем:** таблицы `categories` (дерево), `shops`, `shop_staff`, `products`, `product_variants`. Цены в дирамах (long). Одно активное место — один магазин (уникальный индекс). Публичные: `GET /shops/{id}`, `GET /shops/{id}/products`, `GET /products/{id}`, `GET /categories`. Для продавца: `POST /seller/shops` (статус «на проверке»), `PATCH /seller/shops/{id}`, CRUD `/seller/products`. Проверка прав: менять магазин и товары могут только его сотрудники (иначе 403). Мягкое удаление.
**Проверка:** продавец регистрирует магазин, админ одобряет, продавец добавляет 3 товара; чужой пользователь получает 403 при попытке изменить товар.

### [ ] 1.4. Модуль media — фото
**Что делаем:** `POST /media/upload-url` выдаёт временную ссылку для загрузки в MinIO. После загрузки сервер проверяет тип файла по содержимому (JPEG/PNG/WebP, до 10 МБ), удаляет EXIF и делает миниатюры 200 и 600 px. Привязка фото к магазину и товару.
**Проверка:** загрузить фото товара, открыть оригинал и миниатюры по ссылкам; EXIF в результате отсутствует.

### [ ] 1.5. Модуль search — поиск
**Что делаем:** по разделу 4.1 из ПЗ: нормализация запроса (регистр, ё→е, таджикские буквы), транслитерация латиницы в кириллицу, таблица `search_synonyms`, GIN-индексы pg_trgm и полнотекстовый поиск, ранжирование по формуле из ПЗ (веса в настройках), фильтры (категория, цена, «открыто сейчас», опт/розница), пагинация по 20. `GET /search`, `GET /search/suggest`. Журнал запросов, особенно без результата.
**Проверка:** заполнить тестовые данные; «кросовки», «krossovki» и «пойафзол» находят магазин обуви; запрос без результата попадает в журнал. Тесты на каждый случай.

### [ ] 1.6. Загрузка начальных данных
**Что делаем:** команда (или админ-эндпоинт) импорта магазинов из CSV: ряд, номер места, название, категории, телефон. Шаблон CSV в `docs/shops_template.csv`. Отчёт: сколько загружено, какие строки с ошибками и почему.
**Проверка:** загрузить файл с данными, которые вы собрали на базаре; магазины видны через API.

### [ ] 1.7. Админ-панель (первая версия)
**Что делаем:** веб-панель на Thymeleaf + HTMX внутри Spring Boot по адресу `/admin`. Вход по логину и паролю (BCrypt) с двухфакторной защитой TOTP. Страницы: базары, ряды и места (таблицей, без визуального редактора), очередь магазинов на проверку (одобрить/отклонить), категории, синонимы поиска, пользователи (заблокировать). Журнал действий `audit_log`.
**Проверка:** войти в админку, одобрить магазин, добавить синоним; действия появились в журнале.

### [ ] 1.8. Развёртывание на сервер
**Что делаем:** `Dockerfile` для бэкенда, `docker-compose.prod.yml` (nginx, api, postgres, minio, backup), конфиг nginx с HTTPS (Let's Encrypt) и проксированием WebSocket, ночной бэкап базы, инструкция `docs/DEPLOY.md` по шагам для Ubuntu 24.04.
**Проверка:** по инструкции поднять сервер на VPS; `https://ваш-домен/actuator/health` отвечает UP.

### Мобильное приложение

### [ ] 1.9. Каркас Flutter-приложения
**Что делаем:** проект `mobile/`. Структура `core/` + `features/` (data → domain → presentation). Riverpod, Dio с автоматическим обновлением токена, go_router, хранение токенов в secure storage, локализация (таджикский, русский, узбекский, английский), светлая и тёмная тема, крупный шрифт. Адрес сервера через настройки сборки (dev/prod).
**Проверка:** приложение запускается на эмуляторе Android, переключается язык.

### [ ] 1.10. Вход и главные экраны покупателя
**Что делаем:** вход по номеру и SMS-коду; выбор базара; главная (строка поиска, категории); экран поиска с подсказками, фильтрами и историей; карточка магазина (ряд и номер крупно, фото, часы работы, «Позвонить», «Поделиться»); карточка товара. Гость может искать без входа.
**Проверка:** на телефоне найти товар, открыть магазин, позвонить продавцу.

### [ ] 1.11. Схема базара
**Что делаем:** экран схемы на CustomPainter: ряды, места, точки интереса, масштабирование и перемещение пальцами, подсветка найденного магазина, нажатие на место открывает магазин. Кнопка «Показать на схеме» из карточки магазина.
**Проверка:** из карточки магазина перейти на схему — место подсвечено; на дешёвом Android схема не тормозит.

### [ ] 1.12. Режим продавца в приложении
**Что делаем:** «Мой магазин»: регистрация магазина с выбором ряда и места на схеме, добавление товара с камеры за 30 секунд (фото сжимается до 1600 px до загрузки), варианты (размер, цвет), переключатели «нет в наличии» и «сегодня закрыто».
**Проверка:** засечь время: товар с фото добавляется не дольше 30 секунд.

### [ ] 1.13. Пилот (проверка 2)
**Что делаем:** сборка APK для тестеров, экран «Сообщить об ошибке», Sentry в приложении и на сервере. Чек-лист пилота в `docs/PILOT.md`.
**Проверка:** 20 покупателей и 10–15 продавцов пользуются неделю; собрать отзывы и ошибки, исправить главное. **Не переходите к этапу 2, пока тестеры не находят товары уверенно.**

## Этап 2. Чат и запуск (≈ 4–6 недель)

### [ ] 2.1. Чат на сервере
**Что делаем:** таблицы `chats`, `messages`. WebSocket + STOMP (`/ws`, `/topic/chats/{id}`) с авторизацией по JWT. Типы сообщений: текст, фото, голосовое, карточка товара. Статусы «отправлено / доставлено / прочитано», «печатает…». Сообщение сначала сохраняется в базу, потом доставляется (раздел 5.3 ПЗ). REST: список чатов, история с пагинацией, отметка о прочтении. Чат видят только участники. Лимит новых чатов в день. Автоответ, когда магазин закрыт; готовые ответы продавца.
**Проверка:** два клиента (например, две вкладки с тестовой страницей) переписываются в реальном времени; посторонний получает 403.

### [ ] 2.2. Push-уведомления
**Что делаем:** Firebase Admin SDK, регистрация токенов устройств, push о новом сообщении, если получатель не в сети; шаблоны на 4 языках.
**Проверка:** при закрытом приложении приходит push о новом сообщении.

### [ ] 2.3. Чат в приложении
**Что делаем:** список чатов, экран переписки, отправка фото и голосовых (до 2 минут), карточка товара в чате, статусы, офлайн-очередь (сообщение без связи уходит само, когда появится интернет), кнопки «Написать» в карточках, «Заблокировать» и «Пожаловаться», предупреждение о предоплате.
**Проверка:** включить режим полёта, написать сообщение, выключить режим — сообщение ушло.

### [ ] 2.4. Отзывы, избранное, списки покупок
**Что делаем:** сервер и приложение: отзывы с рейтингом и фото (только после чата с магазином), ответ продавца, жалобы на отзывы; избранные магазины и товары; списки покупок с галочками.
**Проверка:** без чата отзыв оставить нельзя; после чата — можно.

### [ ] 2.5. Маршрут «Как дойти»
**Что делаем:** таблицы `map_nodes`, `map_edges`; простой редактор проходов в админке (клик по схеме ставит точку, второй клик соединяет); привязка мест к ближайшему проходу; A* на сервере (`GET /bazaars/{id}/route`) и такой же алгоритм на Dart в приложении; линия маршрута на схеме и текстовые подсказки («через 40 м налево»). Раздел 4.2 ПЗ.
**Проверка:** маршрут от главного входа до магазина совпадает с реальным путём по базару.

### [ ] 2.6. Офлайн-режим
**Что делаем:** пакет схемы и каталога с номером версии (`GET /bazaars/{id}/map` + каталог магазинов), локальная база Drift в приложении, обновление только изменений, поиск по сохранённым данным без интернета.
**Проверка:** в режиме полёта работают схема, поиск магазинов и маршрут.

### [ ] 2.7. Публикация (проверка 3)
**Что делаем:** удаление аккаунта из приложения, страница политики конфиденциальности, иконки и скриншоты, сборка iOS через Codemagic, чек-лист публикации в `docs/RELEASE.md`. Подключить настоящий SMS-провайдер вместо заглушки.
**Проверка:** приложение прошло проверку Google Play и App Store.

## Этап 3. Рост и доход (≈ 6–8 недель)

### [ ] 3.1. Бронь и торг в чате
**Что делаем:** таблица `reservations`, состояния из раздела 4.4 ПЗ, запрещённые переходы → 409, планировщик (истечение брони, напоминание за 30 минут); в чате кнопки «Отложить до…» и «Предложить цену».
**Проверка:** бронь истекает сама по таймеру; продавец не может выдать отменённую бронь.

### [ ] 3.2. Акции, тарифы, продвижение
**Что делаем:** таблицы `promotions`, `subscriptions`, `payments`; бесплатный и платный тарифы, подъём в поиске с пометкой «Реклама», баннеры, ручное подтверждение оплаты в админке; QR-код магазина для печати.
**Проверка:** оплаченный подъём поднимает магазин в выдаче и показывает пометку.

### [ ] 3.3. Статистика и аналитика
**Что делаем:** статистика продавца (просмотры, звонки, «Как дойти», чаты, брони, «что ищут и не находят»), аналитика админа (пользователи, популярные запросы, запросы без результата, доход), выгрузка CSV.
**Проверка:** цифры в статистике совпадают с действиями, сделанными вручную.

### [ ] 3.4. Импорт товаров из Excel
**Что делаем:** `POST /seller/products/import` (Apache POI), шаблон Excel, отчёт об ошибках по строкам.
**Проверка:** загрузить 100 товаров одним файлом.

### [ ] 3.5. Обход по списку покупок
**Что делаем:** маршрут через несколько магазинов (раздел 4.3 ПЗ: полный перебор до 8 магазинов, дальше «ближайший сосед» + 2-opt).
**Проверка:** маршрут по 5 магазинам короче, чем обход в порядке списка.

### [ ] 3.6. Надёжность и безопасность
**Что делаем:** нагрузочный тест k6 (1 000 пользователей, поиск ≤ 500 мс), проверка OWASP ZAP, исправление найденного, проверка восстановления из бэкапа, Redis для чата, если нужен второй сервер.
**Проверка:** отчёты нагрузочного теста и проверки безопасности в `docs/`.
