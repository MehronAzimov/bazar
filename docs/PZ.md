# Базар-навигатор: пояснительная записка

7 октября 2026

Пояснительная записка к программному комплексу «Базар-навигатор» составлена по структуре ГОСТ 19.404-79 и раскрывает решения, принятые в техническом задании.

## 1. Введение

**Наименование:** программный комплекс «Базар-навигатор» — серверная часть, мобильные приложения для Android и iOS и веб-панель администратора.

**Основание для разработки:** техническое задание «Базар-навигатор» от 7 октября 2026 г.

**Актуальность.** Крупные базары Таджикистана насчитывают сотни и тысячи торговых мест в десятках рядов. Магазины одного товара разбросаны по разным рядам, справочной службы нет, поэтому покупатель теряет время, а продавец в дальнем ряду теряет клиентов. Существующие карты (Google Maps, 2GIS) показывают базар как одну точку и не знают рядов, мест и ассортимента.

**Краткая характеристика.** Комплекс позволяет найти товар или магазин, увидеть его ряд и номер на схеме базара, построить пеший маршрут, написать продавцу в чат и забронировать товар. Продавцы сами ведут витрину, администратор управляет схемами базаров и модерацией.

## 2. Назначение и область применения

**Функциональное назначение:** сократить время поиска товара на базаре и дать продавцам канал привлечения покупателей и связи с ними.

**Эксплуатационное назначение:** комплекс эксплуатируется как общедоступный сервис: приложения распространяются через Google Play и App Store, сервер работает круглосуточно.

**Область применения:** розничная и оптовая торговля на рынках и в торговых центрах с рядной застройкой. Первая площадка — один крупный базар Душанбе, далее другие базары и города (Худжанд, Бохтар, Куляб) без изменения кода.

## 4. Описание алгоритмов

Ключевых алгоритмов четыре: поиск с опечатками, маршрут по схеме, обход по списку покупок и жизненный цикл брони.

**4.1. Поиск с учётом опечаток**

1. Нормализация запроса: нижний регистр, замена ё→е, удаление знаков препинания; таджикские буквы (ҳ, қ, ҷ, ғ, ӣ, ӯ) дополнительно приводятся к русским аналогам.
2. Транслитерация: запрос латиницей («krossovki») переводится в кириллицу и ищется в обоих вариантах.
3. Расширение синонимами из таблицы `search_synonyms` («зарядка» → «адаптер», «пойафзол» → «обувь»).
4. Поиск кандидатов в PostgreSQL: полнотекстовый индекс + триграммное сходство `pg_trgm` (порог 0,3) по названиям товаров, магазинов и категорий.
5. Ранжирование по суммарной оценке (формула ниже), применение фильтров, постраничная выдача по 20 записей.
6. Запрос без результата сохраняется для аналитики, пользователю предлагается «Спросить всех продавцов».

```
S = 0,5 · sim + 0,2 · (rating / 5) + 0,1 · fresh + 0,1 · open + 0,1 · promo
```

Здесь sim — текстовое сходство (0–1), rating — рейтинг магазина, fresh = 1, если товар обновлялся менее 60 дней назад, open = 1, если магазин сейчас открыт, promo = 1 при оплаченном поднятии. Продвигаемые магазины помечаются «Реклама»; веса настраиваются в админке.

**4.2. Построение маршрута по базару**

GPS внутри крытых рядов неточен (погрешность 10–30 м), поэтому маршрут строится по графу проходов, а стартовую точку пользователь выбирает сам (вход или «я у ряда N»).

1. Администратор размечает проходы: узлы (`map_nodes`) — перекрёстки и входы, рёбра (`map_edges`) — отрезки проходов с длиной в метрах.
2. Каждое место привязывается к ближайшему ребру (проекция точки на отрезок).
3. Кратчайший путь ищется алгоритмом A* с евклидовой эвристикой; сложность O(E log V), для базара из нескольких тысяч узлов — миллисекунды.
4. Путь преобразуется в линию на схеме и текстовые подсказки: поворот определяется по знаку векторного произведения соседних отрезков («через 40 м налево, магазин справа»).
5. Граф целиком скачивается в приложение, поэтому маршрут строится и без интернета (тот же алгоритм на Dart).

**4.3. Обход по списку покупок**

Задача обхода N магазинов — вариант задачи коммивояжёра. Для N ≤ 8 перебираются все порядки (до 40 320), для больших — «ближайший сосед» с улучшением 2-opt. Расстояния между магазинами берутся из A* (п.4.2).

**4.4. Жизненный цикл брони**

Состояния: «ожидает» → «подтверждена» → «выдана»; из «ожидает» и «подтверждена» возможен переход в «отменена» (любой стороной) и «истекла» (по таймеру). Планировщик (`@Scheduled`, раз в минуту) переводит просроченные брони в «истекла» и за 30 минут до срока шлёт напоминание обеим сторонам. Запрещённые переходы отклоняются сервером с кодом 409.

## 5. Архитектура и структура программы

Комплекс построен по трёхзвенной схеме: клиенты (приложения Flutter и веб-админка) → сервер Spring Boot (модульный монолит) → хранилища данных. Общая схема компонентов приведена в ТЗ; модульный монолит выбран вместо микросервисов, потому что его проще развивать одному разработчику и дешевле содержать.

**5.1. Модули сервера** (пакет `tj.bazar`, в каждом слои controller → service → repository)

| Модуль | Отвечает за |
| --- | --- |
| `auth` | SMS-коды, JWT, роли, ограничение запросов |
| `user` | профиль, язык, устройства для push, удаление аккаунта |
| `map` | базары, ряды, места, граф проходов, маршруты (A*), офлайн-пакет |
| `catalog` | магазины, товары, варианты, категории, импорт Excel |
| `search` | нормализация, транслит, синонимы, ранжирование, журнал запросов |
| `chat` | WebSocket/STOMP, сообщения, статусы, предложения цены |
| `reservation` | брони, таймеры, напоминания |
| `review` | отзывы, рейтинг, ответы продавца |
| `media` | загрузка файлов, миниатюры, очистка EXIF |
| `notification` | push через Firebase, шаблоны на 4 языках |
| `billing` | тарифы, подписки, продвижение, платежи |
| `admin` | веб-панель, модерация, жалобы, аналитика, журнал действий |

**5.2. Структура мобильного приложения**

Приложение разделено на фичи (`features/search`, `map`, `shop`, `chat`, `favorites`, `seller`, `profile`) и общий слой `core` (сеть, авторизация, локальная база, переводы, тема). В каждой фиче три слоя: data (API и локальный кэш) → domain (модели и логика) → presentation (экраны и провайдеры Riverpod). Продавец и покупатель пользуются одним приложением, режим «Мой магазин» появляется после регистрации магазина.

**5.3. Поток сообщения в чате**

1. Покупатель пишет сообщение (по WebSocket или REST).
2. Сервер проверяет права: является ли отправитель участником чата, не превышены ли лимиты.
3. Сообщение сохраняется в базу со статусом «отправлено».
4. Проверка: продавец в сети?
   - **да** → доставка по WebSocket менее чем за 1 секунду;
   - **нет** → push-уведомление через Firebase на телефон.
5. Продавец открывает чат → покупателю приходит статус «прочитано».

Сообщение всегда сначала записывается в базу, поэтому не теряется при обрыве связи: продавец в сети получает его мгновенно, а не в сети — через push и подгрузку истории при открытии чата.

## 6. Организация входных и выходных данных

Все данные передаются в формате JSON (UTF-8) по HTTPS; даты — ISO 8601 в UTC, деньги — целым числом в дирамах (1 сомони = 100 дирам), чтобы избежать ошибок округления.

**6.1. Входные данные**

| Источник | Данные | Проверка |
| --- | --- | --- |
| Покупатель | номер телефона, поисковые запросы, сообщения, отзывы, брони | формат +992XXXXXXXXX; запрос до 100 символов; сообщение до 2 000 символов |
| Продавец | данные магазина, товары, цены, фото, файл Excel | цена > 0; фото JPEG/PNG/WebP до 10 МБ; до 10 фото на товар |
| Администратор | план базара (изображение), разметка рядов, мест и проходов, справочники | граф проходов связный; номер места уникален в ряду |
| Внешние сервисы | статус доставки SMS, токены устройств Firebase | подпись и срок действия |

Фото сжимается на телефоне до 1600 пикселей по длинной стороне; сервер делает миниатюры 200 и 600 пикселей и удаляет метаданные EXIF (в том числе геолокацию).

**6.2. Выходные данные**

- Результаты поиска: список товаров и магазинов с рядом, номером, ценой и координатами на схеме.
- Пакет схемы базара для офлайна: ряды, места, точки интереса, граф проходов и каталог магазинов с номером версии (обновляется только изменившееся).
- Маршрут: последовательность точек, длина в метрах, текстовые подсказки.
- Сообщения чата и события («печатает», «прочитано») через WebSocket; push-уведомления.
- Отчёты: статистика продавца за день, неделю, месяц; выгрузка аналитики администратора в CSV.
- Ошибки — в едином формате RFC 7807 (код, сообщение на языке пользователя, поле с ошибкой).

**6.3. Структура базы данных**

База данных PostgreSQL содержит 26 таблиц, полный перечень с полями приведён в ТЗ (раздел «Модель базы данных»). Иерархия: город → базар → ряд → место → магазин → товар → вариант. Основные индексы:

| Таблица | Индекс | Для чего |
| --- | --- | --- |
| `products` | GIN (title gin_trgm_ops), GIN tsvector | поиск с опечатками |
| `products` | (shop_id, in_stock) | товары магазина |
| `shops` | (place_id) UNIQUE для активных | одно место — один магазин |
| `messages` | (chat_id, created_at DESC) | история чата по страницам |
| `chats` | (buyer_id, shop_id) UNIQUE | один чат на пару |
| `reservations` | (status, until) | поиск просроченных |

Схема изменяется только через миграции Flyway; удаление магазинов и товаров — мягкое (поле deleted_at), чтобы не терять историю чатов и отзывов.

## 8. Безопасность и защита данных

Комплекс хранит номера телефонов и личную переписку, поэтому защита построена на принципе минимальных прав: каждый видит только свои данные.

| Угроза | Мера защиты |
| --- | --- |
| Перехват трафика | только HTTPS/WSS (TLS 1.2+), HSTS |
| Подбор SMS-кода | код из 6 цифр, живёт 5 минут, 5 попыток, хранится в виде хеша |
| SMS-флуд (трата денег на SMS) | не более 5 кодов в час на номер и 20 на IP, капча после превышения |
| Кража токена | access-токен 15 минут, refresh с ротацией; хранение в Keychain / Android Keystore |
| Доступ к чужим данным | проверка владельца на каждом запросе (чат — только участникам, товар — только сотрудникам магазина) |
| SQL-инъекции | только параметризованные запросы JPA |
| Вредоносные файлы | проверка типа по содержимому, перекодирование изображений, запрет исполняемых файлов |
| Спам и мошенничество в чате | лимит новых чатов в день, жалобы, блокировка, предупреждение о предоплате |
| Взлом админки | двухфакторная аутентификация (TOTP), журнал действий |
| Потеря данных | ежедневный бэкап базы и файлов на другой сервер, проверка восстановления раз в месяц |

**Персональные данные.** Собирается минимум: номер телефона и имя. Номер покупателя не показывается продавцу без согласия. Пользователь может удалить аккаунт из приложения (требование Google Play и App Store). До запуска нужно опубликовать политику конфиденциальности и проверить с юристом требования законодательства Республики Таджикистан о защите персональных данных.

## 9. Тестирование и приёмка

Каждый этап считается завершённым, когда проходят автоматические тесты и выполнены приёмочные сценарии на реальном базаре.

**9.1. Виды тестирования**

| Вид | Средство | Что проверяется |
| --- | --- | --- |

| Интеграционное | Testcontainers (настоящий PostgreSQL) | запросы поиска, миграции, API целиком |
| Нагрузочное | k6 или JMeter | 1 000 пользователей, поиск ≤ 500 мс |
| Интерфейса | integration_test (Flutter) | вход, поиск, чат, бронь на эмуляторе |
| Безопасности | OWASP ZAP, ручная проверка | доступ к чужим чатам и товарам, лимиты SMS |
| Полевое (пилот) | 20 покупателей, 10–15 продавцов | удобство, связь внутри базара, дешёвые телефоны |

**9.2. Приёмочные сценарии**

- [ ] Новый пользователь входит по номеру телефона менее чем за 1 минуту
- [ ] По запросу с опечаткой («кросовки») находятся нужные магазины
- [ ] Тестер находит незнакомый магазин на базаре по маршруту быстрее, чем без приложения
- [ ] Схема и поиск работают в режиме полёта
- [ ] Продавец добавляет товар с фото за 30 секунд
- [ ] Сообщение в чате доходит за 1 с, при закрытом приложении приходит push
- [ ] Сообщение, написанное без связи, уходит после появления интернета
- [ ] Бронь автоматически истекает по таймеру
- [ ] Пользователь не может прочитать чужой чат или изменить чужой товар (ответ 403)
- [ ] Приложения прошли проверку Google Play и App Store

## 10. Развёртывание и сопровождение

На старте всё работает на одном VPS в Docker-контейнерах; при росте база данных и файлы выносятся на отдельные серверы, а серверов приложения становится несколько (с Redis для чата).

**10.1. Состав на сервере (docker-compose)**

| Контейнер | Назначение |
| --- | --- |
| `nginx` | HTTPS (Let's Encrypt), прокси для API и WebSocket, раздача админки |
| `api` | приложение Spring Boot (JAR, Java 21) |
| `postgres` | база данных, данные на отдельном томе |
| `minio` | хранилище фото и голосовых |
| `backup` | ночной pg_dump и копия файлов на внешний сервер |
| `uptime-kuma` | проверка доступности, уведомление в Telegram |

**10.2. Порядок выпуска версии**

1. Изменения делаются в отдельной ветке Git, GitHub Actions запускает тесты.
2. После слияния в main собирается Docker-образ и выкатывается на тестовый сервер.
3. После ручной проверки — выкатка на рабочий сервер; Flyway сам применяет миграции.
4. Мобильные версии: сначала закрытое тестирование (Google Play Internal Testing, TestFlight), затем поэтапный выпуск 10% → 50% → 100%.
5. API версионируется (`/api/v1`), старые версии приложения продолжают работать; при критичных изменениях — экран «Обновите приложение».

**10.3. Сопровождение**

- Ежедневно: просмотр ошибок в Sentry, очередь модерации и жалоб.
- Еженедельно: запросы без результата → новые синонимы и список магазинов для привлечения; обход базара агентом для сверки данных.
- Ежемесячно: обновление зависимостей и образов, проверка восстановления из бэкапа.
- Документация для продавцов: короткие видеоинструкции на таджикском и русском и памятка A5 для витрины.

**11.2. Ожидаемый доход (гипотеза для проверки)**

Расчёт для одного базара через 6–12 месяцев после запуска:

```
D = N · p · T + R
```

где N — число магазинов в приложении, p — доля платящих, T — средний платёж в месяц, R — реклама и поднятия. Пример: 300 магазинов × 10% × 75 сомони = 2 250 сомони в месяц без учёта рекламы; этого хватает, чтобы покрыть серверы и оплатить агента на базаре. Каждый новый базар добавляет доход при почти нулевых затратах на код.

**11.3. Показатели успеха**

| Показатель | Цель через 6 месяцев после запуска |
| --- | --- |
| Магазинов в приложении | ≥ 50% мест пилотного базара |
| Активных покупателей в месяц | ≥ 5 000 |
